# Contributing

This file is for everyone who changes this repository: people and AI agents alike. Agents should
treat every rule here as part of their instructions.

## Ground rules

- **Independence.** This is an independent, clean-room project. Never copy, open or consult another
  decompilation of this game, leaked SDK or RenderWare/CRI source, or code under an incompatible
  license. Work from the retail DOL, dtk's disassembly, RTTI/vtables, public library code we
  vendor (boost 1.32), and this repository. Invent your own names for anything the game does not
  name itself. Decompilations of *other* games may be consulted only as described under
  [References](#references).
- **License.** Everything you contribute is dedicated to the public domain under CC0 1.0
  (`LICENSE`). Only add third-party code whose license allows it, keep its license file next to
  it, and say so in the commit message.
- **The build is the judge.** A change is good when `ninja` exits 0 and ends with
  `build/GUPE8P/main.dol: OK`. objdiff at 100% is not enough on its own.

## References

Other games' decompilations share our libraries (the Dolphin SDK, the MetroWerks runtime and MSL,
TRK). The CC0 ones listed in [docs/toolchain.md](docs/toolchain.md#reference-material) may be read
to *understand* a library function: what it does, which compiler flags built it, why a match
fails. They are not templates, and this project is not a copy of them.

- Write the code yourself from the disassembly: your own structure, local names, helpers and
  comments. Names the binary or SDK headers fix (function, global and type names, register and
  hardware constants) stay as they are.
- Check every file you wrote while a reference was open:

  ```sh
  python tools/similarity.py --ref path/to/tp --ref path/to/other-reference src/dolphin/os/OSFoo.c
  ```

  Comments, whitespace and `asm` bodies are ignored. A file flagged `TOO CLOSE` (60% or more of
  its code, or 8 or more consecutive lines, the same as a reference) is reworked until it passes.
  Clone the references outside this repository; never commit their files.
- Name every reference you consulted in the commit message (`Reference: zeldaret/tp OSAlarm.c`),
  and add it to the reference table in `docs/toolchain.md` if it is new.

## Sync first, every time

Several people and agents work on this repository at once. Before you start anything, and again
right before you push:

```sh
git fetch origin
git merge origin/main        # or: git pull --rebase
```

Then build if you can (see below). Never push with `--force`; `main` refuses force pushes and
deletion. If a push is rejected because `main` moved, fetch, merge and build again, then push.

Agents running in waves sync at the start of every wave (before seeding worktrees) and again
before each push, so work pushed by others in between is merged first, never overwritten.

## Pull requests

`main` accepts changes from contributors only through pull requests:

1. Work on a branch (in your fork or here), synced with `main` as above.
2. Open a pull request. Its description lists the units and their status, what changed outside
   them, and the references consulted.
3. The **Progress tracker** check must pass, and the branch must be up to date with `main`
   (GitHub offers "Update branch" when it is not).
4. The project owner (2Balanced) reviews and approves it. **Do not merge your own pull request**;
   the owner merges it after approving. Pushing new commits after an approval asks for a new one.

The owner's routine pushes (matching waves, tracker regeneration) go to `main` directly and pass
the same checks locally first.

## Who works on what

- **Game code** (`src/Game/`, the game headers in `include/Game/`, `config/GUPE8P/*`): matching
  work, normally done in waves with a copy of the game.
- **Non-game code** (`tools/`, `.github/`, `docs/` other than the progress tracker, build
  scripts, the MSL stand-ins, `include/boost` housekeeping): maintained mostly by premohq. Agents
  doing game work leave these alone unless their task needs a change, and say so when they make
  one.

When two people need the same file, sync first and keep each change small.

## Files with special rules

| File | Rule |
| ---- | ---- |
| `README.md` | Leave it as it is. Its layout, wording and links are kept deliberately short. Change it only when the project owner asks. |
| `docs/progress.html`, `docs/progress/progress.svg`, `docs/progress/badge.json`, `docs/progress/source.txt` | Generated by the build. Never edit them by hand. Commit them in the same commit as the source change that produced them. |
| `docs/progress/history.jsonl` | Generated, one snapshot per line. Never reorder or rewrite it by hand; the build only appends. |
| `LICENSE`, `include/boost/LICENSE_1_0.txt` | Never change. |
| `config/GUPE8P/splits.txt` | Insert blocks in address order; never reorder existing blocks. |
| `config/GUPE8P/symbols.txt` | Rename only placeholder names (`fn_`, `lbl_`, `@N`) unless the evidence shows a real name is wrong; record the evidence in the commit message. |

## Keeping the progress tracker right

`ninja` regenerates the progress page, the README card (`progress.svg`) and the badge every time it
builds, from the build's own report. To keep them correct when people push at nearly the same time:

- **History is merge-safe.** `history.jsonl` uses git's union merge (`.gitattributes`): when two
  pushes each add a snapshot, both lines are kept and the build re-sorts them.
- **Everything else is regenerated, not merged.** The other progress files are marked not to be
  merged textually. If a merge conflicts on them, take either side (`git checkout --ours
  docs/progress*`), rebuild with `ninja`, and commit the regenerated files with the merge.
- **A check proves it.** The build records a fingerprint of `src/`, `include/`, `config/` and
  `configure.py` in `docs/progress/source.txt`. `python tools/check_progress.py` fails when the
  committed tracker was built from different sources, for example after a merge that brought in
  someone else's units. GitHub Actions runs it on every push, and the pre-push hook runs it before
  yours. Enable the hook once per clone:

  ```sh
  git config core.hooksPath tools/hooks
  ```

- **Include it in your change.** If you can build, every commit or pull request that changes
  `src/`, `include/`, `config/` or `configure.py` also commits the regenerated `docs/progress*`.
  Do not leave it out to avoid conflicts: if `main` moves, update your branch, rebuild, and commit
  the new tracker (a conflict on those files is resolved by rebuilding, never by hand).
- **No game copy?** If you cannot build, do not touch `docs/progress*`; say so in the pull request
  and the owner adds a tracker commit before merging. Changes to `tools/`, `.github/` and `docs/`
  (other than the tracker) do not affect the fingerprint and need no tracker commit.

## Code conventions

- Read `docs/matching-gadgets.md` (how to match a unit, shared types, linking rules) and
  `docs/research-notes.md` (compiler findings and known blockers) before matching anything.
- Line endings: sources and headers under `src/` and `include/` are CRLF; `config/**/*.txt` and the
  progress files are LF. Check after scripted edits (`sed -i` in Git Bash strips CRLF).
- One name per class. If RTTI names a class that the project knows under a placeholder, rename it
  everywhere (`tools/rename_class.py`, `tools/rename_ident.py`) instead of adding a second name.
- Overrides must match the base virtual's return type exactly, or the vtable grows a slot.
- New templates in widely included headers go behind an `#ifdef`, or every unit's compiler-generated
  `@N` locals renumber.
- New units: split block inserted in address order, `Object(...)` entry in alphabetical order in
  `configure.py`, `Matching` only when every function and section is 100% and `main.dol` is OK.

## Commits

- Commit with your GitHub noreply address (`git config user.email <id>+<login>@users.noreply.github.com`).
- Subject line in the imperative, under about 72 characters; the body says what changed and why,
  lists units that became Matching or NonMatching (with N/M), and any renames outside a unit's own
  range.
- Work produced with an AI assistant carries a `Co-Authored-By:` trailer naming it.
- Code written with a reference open names it in a `Reference:` line (see [References](#references)).
  The pull request description alone is not enough: the commit history is the lasting record.
